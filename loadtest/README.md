# Relationship policy load test

`relationship_policies.py` measures the policies generated by
`Policy.from_relationship` against other ways of writing the same rule,
including `STABLE SECURITY DEFINER` helper functions. See its docstring for
the schema and the variants.

```bash
pip install -e ".[dev]"
python -m loadtest.relationship_policies --scale 1 --accounts 1000 --repeats 5 --sample-accounts 5
python -m loadtest.relationship_policies --explain chapters.count --variants generated definer_array
```

It starts a throwaway Postgres (`testing.postgresql`), loads the data,
switches the policies of `books`, `chapters` and `articles` between variants,
and reports the server execution time (`EXPLAIN (ANALYZE, TIMING OFF)`) of
each query, run as a non-owner role with RLS forced. Writes run in a
savepoint that is rolled back, followed by a `VACUUM`, so each run sees the
same data. Each query's results (or, for the `_denied` queries, whether
Postgres rejected the write) are compared with the generated policy's, and a
variant that implements the rule differently is flagged with `≠`.

## Variants

| variant | `books` policy (`chapters` and `articles` are analogous) |
|---|---|
| `none` | `true`: RLS applies but does not filter (baseline) |
| `denormalized` | `account_id = <context>` on a denormalized column |
| `generated` | `EXISTS (SELECT 1 FROM authors WHERE authors.id = books.author_id)`, as generated |
| `in_subquery` | `author_id IN (SELECT id FROM authors)` |
| `definer_per_row` | `rls_author_visible(author_id)`, a `STABLE SECURITY DEFINER` function |
| `definer_array` | `author_id = ANY ((SELECT rls_accessible_author_ids())::integer[])`, a `STABLE SECURITY DEFINER` function evaluated once |

`authors`, `tags` and `article_tags` keep the same policies in every
variant. `article_tags` has the policies generated by
`from_relationship("tags", link_policies=True)`, whose write policies call
`rls_visible_articles_id_<hash>` and so check `articles` through the variant's policy.

Every variant keeps the generated policies' `OR <bypass_rls>` clause. The
`SECURITY DEFINER` functions bypass RLS on the tables they read, so they have
to re-implement the related tables' rules. The other variants read the
related tables through those tables' own policies.

## Queries

| query | what it does |
|---|---|
| `count` | `SELECT count(*)`: a full scan |
| `point` | one row by primary key |
| `by_fk` | the rows of one visible parent (one tag for `articles`) |
| `page` | the first 50 rows by id |
| `insert_one` / `insert_batch` | insert 1 / 500 rows under visible parents |
| `update_reparent` | move a row to another visible parent |
| `insert_denied` | insert a row under another account's parent (must be rejected) |
| `update_one` / `update_all` | update one row / every row the account can see |
| `upsert_one` / `upsert_batch` | `INSERT … ON CONFLICT DO UPDATE` of 1 / up to 500 existing visible rows |
| `link_insert_one` / `link_insert_batch` | insert 1 / 500 `article_tags` links between visible articles and tags |
| `link_delete_one` | delete one visible link |
| `link_insert_denied` | link a hidden article to a visible tag (must be rejected) |

## Findings

**The generated policies do not need `SECURITY DEFINER`.**

### Reads

- **Point lookups and foreign-key filters** cost the same as with a
  denormalized column (0.01–0.03 ms, 0.2 ms for `articles.by_fk`). The
  `EXISTS` becomes an index probe of the related table for the few rows the
  query reads.
- **Scans** (count, page): Postgres turns the correlated `EXISTS` into a
  hashed subplan (`ANY (book_id = (hashed SubPlan))` in the plan). The visible
  related ids are computed once per query and each row is checked with a hash
  lookup, so the per-row subquery the policy appears to describe never runs.
  A one-level relationship (`books`) costs about the same as a denormalized
  column. Each further level of a chain adds another hashed subplan:
  `chapters` → `books` → `authors` is 2.3–2.8x slower than denormalized
  (`chapters.count`: about 150–170 ms against 55–75 ms).
- **Pages at 10% visibility** are where a denormalized column wins clearly
  (0.1 ms against 3–24 ms). It reads 50 rows from the index and stops, while
  the generated policy first builds the hash of visible parents.
  `definer_per_row` is also faster there (1.7–4 ms), but loses everywhere
  else.
- **`definer_per_row` is 30–45x slower on counts.** Postgres never inlines
  `SECURITY DEFINER` functions, so the function runs once per row and none of
  the planner's rewrites apply.
- **`definer_array` is competitive only when an account sees few rows.**
  `= ANY (array)` with a non-constant array is a linear search per row.
- **`in_subquery`** (the same rule as `generated`, written uncorrelated)
  wins slightly on full scans, since it parallelizes. It loses badly on
  point lookups and single-row writes (3–60 ms against 0.03–0.3 ms), because
  it always builds the full hash of visible parents.
- `articles.count` at 10% visibility measured 551 ms here, 85 ms in an earlier
  run and 137 ms as a single `EXPLAIN ANALYZE`, with the same hashed-subplan
  plan. Treat it as noisy.

### Writes

The generated policies check writes with the same expression as reads (they
are `FOR ALL` policies without a separate `WITH CHECK`), so an inserted or
updated row must point at a parent the session can see. `insert_denied` is
rejected by every variant except `denormalized`.

- **Single-row inserts, updates and upserts** through the chain cost
  0.1–0.3 ms, within about 0.1 ms of no filtering. The new row's parent is
  checked with one index probe per level.
- **Batches of 500** cost about 10–20 µs more per row than no filtering.
  `chapters.upsert_batch` is the most expensive: about 10 ms against 5 ms.
- **`update_all`** costs about what the matching scan costs, plus the update
  itself (`chapters`: 176 ms at 0.1% visibility, 1.3 s for the 100k rows of
  an account at 10%).
- **`definer_per_row`** is slower on every write, by 1.5–2x on batches and
  30x on `update_all`.

### Many-to-many links

The `link_policies=True` write policies call `rls_visible_articles_id_<hash>` for
each link to check the article, then check the tag with an `EXISTS`. The
function is generated for the `articles` table with a fixed query, so
PL/pgSQL caches its plan.

The `link_*` rows in the tables above were measured with an earlier version
that used one generic function building its query dynamically
(`EXECUTE format(...)`), which Postgres planned again for every link. A
separate run with the per-table function, at both visibility levels:

| query | none | generated | definer_per_row |
|---|---|---|---|
| articles.link_insert_one | 0.17 | 0.17–0.19 | 0.18 |
| articles.link_insert_batch | 8.0–8.2 | 14.7–14.8 | 11.9–12.5 |
| articles.link_delete_one | 0.10 | 0.42–0.46 | 0.30 |

- **One link** costs about the same as no check.
- **A batch of 500 links** costs about 7 ms more than no check (about 15 µs
  per link), against 105 ms more with the generic function.
- **Deleting a link** costs about 0.3 ms more, since a delete checks the
  link against both the `SELECT` and the `DELETE` policies.
- With `in_subquery`, each call builds the full hash of visible articles:
  1.9 s for 500 links with the generic function.

### Things to watch

- **Deep chains on large tables.** The cost of a scan grows with the
  depth of the chain. On hot tables, denormalizing the owning key (or using
  `condition_arg` on a direct foreign key) is still the fastest option, as
  long as the denormalized key is itself kept correct.
- **Row estimates.** The planner estimates that these policies keep a large
  fraction of rows (750,000 estimated against about 1,000 actual for
  `chapters.count` at 0.1% visibility), partly because of the
  `OR <bypass_rls>` clause. This did not cause bad plans in these
  single-table queries. In larger joins it can lead the planner to the wrong
  join order or method, so check `EXPLAIN` on important queries.
- **Indexes.** The fast paths rely on the related table's primary key
  (many-to-one), and on an index whose first column is the row's key in the
  association table (many-to-many; here the `(article_id, tag_id)` primary
  key, plus an index on `tag_id`, which builds the set of visible articles
  from the visible tags).
